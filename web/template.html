Well-clear detection, regenerated from its own requirements.

This study takes one component of DAIDALUS, NASA's open-source detect-and-avoid library, through a complete regeneration workflow. Requirements are derived from the source code and encoded as an exact executable model, and a new implementation is written in Rust from the requirements. The original and the new implementation are then checked against the model on encounters.

Component

DO-365 defines when an unmanned aircraft is no longer well clear of another aircraft. DAIDALUS, NASA's reference implementation of the DO-365 detect-and-avoid logic, makes this decision in the classes WCV_TAUMOD (horizontal, modified tau) and WCV_TCOA (vertical). Given the positions and velocities of both aircraft, the component returns the time interval within the lookahead window during which they will not be well clear, assuming straight-line flight.

DefinitionsSI units, s = sown − sint
Relative
s = so − si and v = vo − vi (SEM-1)
Horizontal
|s| ≤ DTHR, or HMD ≤ DTHR and 0 ≤ τmod ≤ TTHR, where τmod = (DTHR² − |s|²) / (s·v) when closing (SEM-2)
Vertical
|sz| ≤ ZTHR, or 0 ≤ tcoa ≤ TCOA, where tcoa = −sz / vz when converging (SEM-3)
Detection
the times t in [B, T] at which both conditions hold at s + t·v, proved in PVS to form one closed interval (SEM-5)
Defaults
DO-365 DWC Phase I: DTHR 0.66 nmi, ZTHR 450 ft, TTHR 35 s, TCOA 0 s; lookahead 180 s

Derived Requirements

Each of the 24 requirements is traced to upstream source lines and compared with the PVS specification. A requirement that agrees has the same meaning as the specification in exact arithmetic; a convention is behavior that the code adds (tolerances and boundary handling) and that the specification does not have; an assumption is a precondition that the specification states and that the code does not enforce. Select a row to show the requirement, its sources, and the evidence for its status.

Checks Against the Exact Model

Inside the boundary band, where an exact answer changes discontinuously under a perturbation of one unit in the last place, any floating-point implementation may decide either way. Decisions there are recorded rather than graded.

Limitations
    Further work
    • Repeat the regeneration with isolated contexts: one agent derives the requirements, a second regenerates the component from the requirements and the PVS specification alone, and the checker is unchanged.
    • Extend the thread to WCV_TAUMOD_SUM and the bands layer, and then replay the DAIDALUS Regression scenarios end to end.
    • Carry the Lean proofs to the code: generate the Rust and JavaScript implementations from the closed form proved in Lean, compare them bit for bit with the current ones, and bound their rounding error.
    • Measure the recall of code-only derivation against DO-365 Appendix G (a paid RTCA document) to determine what the code alone does not reveal.

    Reproducing the Results

    Every number on this page is taken from results/summary.json, which is generated from the outputs of the commands below. The command make verify fetches DAIDALUS at the pinned commit, runs the exact model and all three implementations on the corpus, and compares every output with the committed checksums and results. It requires Python 3.10 or later, Java 19 or later, Node.js 18 or later, and a Rust toolchain.
